# Architecture and code review — 2026-09-09

## Scope and method

Base: `main` at `1d0dac3`. This is a broad, risk-prioritized review, not a
claim that every branch of every feature has been exhaustively verified.
Reviewed the repository structure, schema/migrations, CI, permission registry,
authentication, financial transaction boundaries, ZATCA generation, HR,
incentives, integration endpoints, file delivery and statistical helpers.
Existing production/inventory regression suites remain part of verification.

The existing, unmerged [production lifecycle PR #2](https://github.com/sayedelbadry84-png/Batchline/pull/2)
is separate work. This branch does not merge, overwrite or certify that PR;
shared files must be reconciled when either branch is merged.

Existing solutions preflight: the repository already has Prisma transactions,
PostgreSQL locks, site-scope helpers, numbering retries and Node tests. Reused
these and PostgreSQL's transaction advisory lock; no new service, framework,
paid dependency or broad rewrite is needed for these fixes.

## Architecture assessment

The modular monolith is suitable for the application's current shape:
Next.js route groups for back office/field clients, Server Actions as request
boundaries, `src/lib` for shared domain calculations and transactional services,
Prisma/PostgreSQL for persisted invariants, and external storage/integration
adapters. Inventory and reservation revision code already demonstrates useful
patterns: immutable snapshots, database constraints, row locking and explicit
regression tests. Those patterns were not consistently applied to finance/HR.

Main architectural deviations:

- Authorization must include record ownership/site, not just module/action role.
- Financial state changes must re-read eligibility after acquiring the same
  lock as competing operations. A preflight read is not an atomic guard.
- Retry boundaries must enclose the entire transaction after a PostgreSQL
  uniqueness/serialization failure, not retry queries in an aborted transaction.
- Related effects (leave approval and attendance) belong in one transaction.
- Pure calculations need database-free tests alongside integration suites.
- Setup documentation must reflect PostgreSQL and migration history, not SQLite.

## Deployment

One additive Prisma-generated migration adds nullable `User.totpLastUsedStep`.
Apply the migration before deploying the new application code; regenerate
Prisma Client as usual. No existing TOTP secrets or sessions are reset.
The migration was generated by diffing the old and new schema, without
connecting to production. Existing generated ZATCA documents are not rewritten:
the new locking prevents future races, but cannot certify/repair an old fork.

## Remaining limitations / follow-up design work

1. **Monetary Float fields:** migrating money to Decimal needs an explicit
   scale/rounding policy, a data reconciliation and tests across invoices,
   payroll, incentives, journals, reports and exports. Quantities are not all
   money. Blindly converting every Float would break application interfaces
   and risk historical values; this PR does not attempt that migration.
2. **Historical ZATCA chain/compliance:** any existing fork or timestamp tie
   requires a read-only data audit and an approved remediation procedure.
   Real clearance, certificate canonicalization and regulator compliance
   were not validated against the external service. Chain scope currently
   follows the application's existing per-site model.
3. **Deployment trust boundary:** `getClientIp` assumes the ingress overwrites
   forwarded headers. That must be checked for the real hosting/proxy chain;
   the review did not inspect its deployment configuration. Per-account
   lockout/TOTP limits do not depend on a trustworthy IP header.
4. **Session secrets at rest:** session identifiers and TOTP seeds remain in
   their existing storage representation. A hashed-session/encrypted-secret
   migration needs a rotation/compatibility plan, not an implicit mass logout.
5. **Other workflows / performance:** financial cancellation rules outside
   customer billing, generic notification endpoint ownership/egress, dynamic
   permission overrides in historically admin-only workflows and concurrent
   administrative ownership transfers deserve follow-up. No full load test,
   query-plan/index study, browser accessibility audit or live integration
   acceptance test was performed. Missing indexes alone are not evidence of
   a measured production performance defect.

The prior local review's statement that anomaly detection can *never* fire
was too broad: the self-inclusion bound explains failure at small sample
counts, not arbitrary history sizes. Likewise, admin-only default actions
are not automatically cross-site exploits; editable grants and actual
request reachability must be considered.
